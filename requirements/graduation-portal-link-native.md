# 포털 연동·재연동 화면의 네이티브 이전

- 작성일: 2026-10-19
- 기준: 웹 저장소 `gyumong/chukchuk-haksa` main `35d5cc6`(2026-10-08), 앱 `poc` 브랜치 `5d57182e`

## 원문 요청

> https://github.com/gyumong/chukchuk-haksa 여기에 있는 졸업학점 인증 기능을 gui 포함해서 이동할거야.
> 기존에 서버에서 인증하던 부분은 fallback으로 두고, 1차로는 이 브랜치에 있는 스크래핑을 우선시 할거야

## 목표

웹앱의 포털 연동 화면(첫 연동)과 정보 업데이트 화면(재연동)을 Compose 네이티브 화면으로 옮긴다.
스크래핑은 이 브랜치의 앱 내부 스크래퍼(`remote/portalscrape`)를 먼저 사용하고, 일부 오류가 발생했을 때만
기존 서버 job(`POST /portal/link`)으로 자동 전환한다.

## 범위

- 포함
  - 포털 ID·비밀번호 입력 폼, 스크래핑 진행 화면, 실패 화면
  - 서버 fallback job 생성과 폴링(`POST /portal/link`, `GET /portal/link/jobs/{jobId}`, `.../summary`)
  - 웹 진입점을 가로채는 브리지 처리
  - 스크래핑 결과 업로드 API의 계약 초안(백엔드 담당자 전달용)
- 제외
  - 졸업 요건 상세 화면(`/mpa/graduation-progress`)과 홈 졸업 요건 카드는 웹에 그대로 둔다.
  - 졸업 요건 계산 로직은 옮기지 않는다.

옮길 웹 화면은 다음과 같다.

| 웹 경로 | 역할 |
|---|---|
| `/mpa/portal-login` | 첫 연동 입력 폼 |
| `/mpa/portal-login/scraping` | 첫 연동 진행·실패 화면. 성공하면 `done:portal-link`를 보낸다 |
| `/mpa/resync/login` | 재연동 입력 폼. 앱에서는 광고 게이트(`AD_GATED_PATHS`)를 거친다 |
| `/mpa/resync/scraping` | 재연동 진행·실패 화면 |

## 데이터 흐름

1. 앱이 포털을 스크래핑해서 `PortalScrapeResult.rawJson`을 만든다. 이 JSON은 서버 스크래퍼가 S3에 저장하던 원문과 구조가 같다.
2. 앱이 새 업로드 엔드포인트로 `rawJson`을 보내면, 서버가 기존 저장·계산 로직으로 DB에 반영한다.
3. 졸업 요건은 지금처럼 `GET /api/graduation/progress`가 계산하고 웹 화면이 표시한다.

현재 서버 경로는 `POST /portal/link` → 스크래핑 워커 → S3 → `POST /internal/scrape-results`(HMAC 서명 콜백) → DB 순서로 진행된다.
내부 콜백은 HMAC 비밀 키가 필요하므로 앱에서 재사용하지 않는다. 앱이 결과를 올릴 엔드포인트(`POST /portal/link/scrape-results`)는
백엔드가 앱 초안대로 구현했다(PR #369, 2026-10-19 기준 Draft이며 배포 전이다).

## 결정 사항

| 질문 | 결정 |
|---|---|
| 네이티브로 옮길 화면 | 포털 연동, 정보 업데이트(재연동) |
| 졸업 요건 판정 위치 | 서버. 앱이 스크래핑 결과를 업로드한다 |
| fallback 조건 | 네트워크 오류나 포털 구조 변경처럼 앱 쪽 문제로 보일 때만 자동 전환한다. `PORTAL_AUTH_FAILED`는 전환하지 않는다 |
| 웹 진입점 처리 | `BridgeAction`이 `/mpa/portal-login`과 `/mpa/resync/login` 이동 요청을 가로채서 네이티브 화면으로 보낸다 |
| 업로드 API 준비 | 앱 쪽에서 계약 초안을 써서 백엔드 담당자에게 넘기고, 앱은 fake 구현으로 먼저 개발한다 |
| 완성 수준 | 플래그 없이 정식 출시한다 |
| 재연동 광고 게이트 | 유지한다. 확인 다이얼로그와 전면 광고를 거친 뒤 네이티브 화면으로 들어간다 |
| 서버 연동 중단 상태 | 앱에 별도 스위치를 두지 않는다. 서버가 거부하면 그 응답을 오류로 보여 준다 |

## 가정 (질문하지 않고 기본값으로 정한 부분)

- Android와 iOS 모두 commonMain 코드로 지원한다.
- 성공하면 기존 `done:portal-link` 처리(`HomeViewModel`)와 똑같이 홈 탭(웹뷰)으로 돌아간다.
- 포털 비밀번호는 기기에 저장하지 않는다.
- POC 확인 화면과 디버그 진입 버튼(Landing 우측 상단, 시간표 탭 우측 하단)은 정식 화면으로 대체한 뒤 정리한다.

## 완료 기준

- 웹 홈에서 첫 연동이나 정보 업데이트를 누르면 네이티브 화면이 열린다. 재연동은 광고 게이트를 통과한 뒤에 열린다.
- 앱 스크래핑이 성공하면 업로드가 끝난 뒤 홈 탭으로 돌아가고, 갱신된 졸업 요건이 보인다.
- fallback 대상 오류가 나면 서버 job을 만들어 폴링하고, 그 결과에 따라 성공 또는 실패를 보여 준다.
- 비밀번호 오류에서는 fallback 없이 오류를 안내한다.
- `./gradlew :shared:testAndroidHostTest :androidApp:assembleDebug`, `./gradlew :shared:linkDebugFrameworkIosSimulatorArm64`,
  `xcodebuild`(iosApp 스킴)가 모두 통과한다.

## 후속 결정 (2026-10-19)

처음 정리할 때 미결로 남긴 세 가지는 다음과 같이 정했다.

1. **웹의 재연동 차단**: 웹의 `SyncUpdateButton`은 `PORTAL_LINK_DISABLED`가 `true`이면 공지 다이얼로그를 띄우고 끝나서,
   지금은 재연동 이동 요청이 앱에 오지 않는다. 웹은 나중에 웹 쪽에서 고친다. 앱은 웹이 이동을 요청하면 가로채도록만 만들어 둔다.
2. **출시 시점**: 사용자가 직접 정한다. 업로드 엔드포인트가 배포되기 전에는 앱 스크래핑이 성공해도 업로드 단계에서 실패한다.
3. **업로드 실패**: 스크래핑을 다시 하지 않고 같은 결과를 다시 올린다. 서버 job으로 넘기지 않는다.
   백엔드 연동 가이드를 반영해서, 같은 결과를 다시 올리는 것은 저장됐는지 알 수 없는 실패(5xx, 네트워크 오류)로 한정했다.
   서버가 4xx로 거부하면 실패 화면을 보여 주고, 다시 시도하면 입력 폼으로 돌아간다.

## 구현 메모

- 가로채기는 `BridgeAction`이 아니라 `MainNavigator.navigateWebView`에서 한다. 웹 홈의 이동 요청, 광고 게이트를 거친 이동,
  랜딩의 미연동 분기, 시간표 탭의 연동 안내 다이얼로그가 모두 이 함수를 지나므로 한 곳에서 처리된다. 광고 게이트는 그대로 동작한다.
- 업로드 API 계약과 앱의 오류 처리는 `requirements/portal-scrape-upload-api.md`에 있다.
- 일부 학기 성적 상세 조회가 실패한(경고가 있는) 스크래핑 결과는 올리지 않고 서버 job으로 넘긴다.
  서버가 올린 결과를 전체 기록으로 보고 빠진 과목을 지우기 때문이다.
- 디버그 빌드에서는 기기를 흔들면 디버그 화면(`presentation/debug`)이 열린다(2026-10-19 사용자 요청).
  여기서 포털 연동 경로를 기본(앱 우선, 서버 fallback)·앱 로직만·서버 로직만 중에서 고르고(`PortalLinkStrategy`),
  연동 여부와 관계없이 첫 연동 화면이나 학업 정보 업데이트 화면을 연다. 고른 경로는 저장하지 않아 앱을 다시 시작하면 기본으로 돌아간다.
  출시 빌드에는 흔들기 감지와 디버그 화면 경로를 등록하지 않는다.
- POC 확인 화면과 디버그 진입 버튼은 지웠다.
